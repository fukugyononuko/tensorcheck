## RCA

### P-01・P-04：レビューのたびに、カバーしていない場合を 1 件ずつ指摘された
- なぜ 1：なぜ指摘が 6 回（PR #45 では 10 回）続いたか → 毎回、主張（または対応する構成）の範囲の外にある入力が 1 つずつ見つかったため。
- なぜ 2：なぜ範囲の外の入力が残っていたか → 主張を「こう動くはず」という理解から書き、実装が実際に保証している条件（`illinois` のコメントにはすでに「ちょうど 0 の点、または括弧の端」と正確に書かれていた）から写さなかった。PR #45 でも、git の動作を理解から真似た。
- なぜ 3：なぜ 1 回の指摘で、ほかの場所も直らなかったか → 同じ主張を 8 か所でそれぞれ言い換えて書いていて、直すたびに残りの言い換えを洗い出す手順がなかった。
- なぜ 4：なぜレビューの前に見つけられなかったか → 主張の文を端の入力に当てて確かめる段がなかった。端の入力の一覧（T-01）を参照せず、一覧にも「評価点がちょうど 0 や特異点に一致する」「積分の向き」「引数の絶対値が大きく丸めが効く」がなかった。
- 根本原因：保証の文を、実装の事後条件から写して 1 か所に置く決まりと、その文を端の入力の一覧に当てて確かめる段がなく、さらに範囲が開いた対象（外部のツールの設定の解釈）を網羅しようとしたため、レビュアーが範囲の外の入力を 1 件ずつ見つける形になった。
- 再発防止策：
  - 保証（事後条件）の正確な文は 1 か所（公開 API の文書か設計書）にだけ書き、ほかの場所は前提と参照だけにする。文は、実装の事後条件（コード中のコメント、テストの条件）から写す（T-01）。
  - 端の入力の一覧に、評価点がちょうど 0 や特異点に一致する場合、積分の向き、引数の絶対値が大きく丸めが効く場合を足す。保証の文を書いたら、一覧の各項目で確かめたか、確かめていない項目を PR に書く（T-02）。
  - 外部のツールの設定の解釈は真似ない。通常の構成だけを扱い、それ以外は安全側に失敗させる（T-03）。

### P-03：修正の前の証拠を返信に書いた
- なぜ 1：なぜ古い結果を書いたか → grep を実行したあとに DD-12 を 1 文直し、grep を取り直さずに返信を書いた。
- なぜ 2：なぜ取り直さなかったか → 証拠を、返信の対象のコミットの状態で取るという決まりがなかった。
- 根本原因：返信や PR に書く証拠を、最後の変更の後に取り直す手順がない。
- 再発防止策：返信と PR の本文に書く照合・テストの結果は、push したコミットの状態で取り直してから書く（T-04）。

### P-06：未レビューのコミットのマージ
- なぜ 1：なぜ未レビューのままマージしたか → skill の手順では、承認なしのマージのあとのレビューは「させてよい」という任意の手順だった。
- 根本原因：承認なしでマージするときに、最後のコミットをレビューする手順が必須でなかった。
- 再発防止策：済み。マージの前に最後のコミットをレビューし、その回の指摘を issue に登録してからマージする（skill `codex-review` の手順 6、PD-018）。
