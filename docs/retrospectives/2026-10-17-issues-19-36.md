## RCA

### P-02：確かめた範囲を広く書いた
- なぜ 1：PR #35 では、上限 0 のテストを 1 つの解法で書き、ほかの解法も同じ経路を通ると考えた。PR #39 では、照合のスクリプトの結果を、スクリプトが正しい前提で読んだ。
- なぜ 2：本文の主張（「すべての解法で」「ERR-01〜22 の補足も」）と、それを支える証拠（テスト、照合の結果）を、対象ごとに並べて突き合わせる手順がなかった。主張は概要に、証拠はテストの節に別々に書いていた。
- なぜ 3：わざと誤りを入れて失敗することを確かめる決まり（開発の決まり 20）は、数値の判定のテストに向けたもので、照合や検査のスクリプト自体には使っていなかった。PR #39 のスクリプトに `—` の行の違いを 1 つ入れれば、見落としに気づけた。
- 根本原因：「すべて」「どの〜でも」と書く主張を、対象を数え上げて 1 つずつ証拠に結びつける手順がなく、証拠に使うスクリプトの検証も手順に入っていなかった。
- 再発防止策：
  - PR の本文で「すべて」「どの〜でも」「両方」と書くときは、対象を列挙し、対象ごとに証拠（テストの名前、照合の結果）を書く。証拠のない対象は「未確認」と書くか、主張を狭める（T-01）。
  - 照合や検査のスクリプトを証拠に使うときは、わざと差を 1 つ入れて、それを検出することを確かめる（T-02）。
  - ERR の表とコードの照合は、手作業ではなく CI で行う（T-03、issue #38）。

### P-01：単位と同じ名前の変数
- なぜ 1：テストの中で、長さを `m`、無次元の値を `one` という名前の変数にした。
- なぜ 2：テストのファイルは単位を名前で import している（`use tensorcheck::units::si::{m, one, s, …}`）。単位はユニット構造体なので、同じ名前の `let` はパターンになる。定数にしても同じで、表現を変えても避けられない。
- 根本原因：単位を名前で import したファイルで、変数の名前と単位の名前がぶつからないようにする決まりがなかった。利用者向けには README の Tips に回避策（`use tensorcheck::units::si as u;`）があるが、開発の決まりにはなかった。
- 再発防止策：テストで単位と同じ名前を変数にしたいときは、README の Tips と同じく単位をモジュールごと import する（`si as u`）。`docs/README.md` の開発の進め方に書く（T-04）。影響はビルド 1 回なので、自動検査はしない。
