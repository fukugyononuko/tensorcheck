# 設計ドキュメント

tensorcheck の設計ドキュメント一式。
アーキテクチャは、Juval Löwy『Righting Software』（Addison-Wesley, 2019）で示された設計の方法 **The Method** に従う。The Method は、システムを機能ごとではなく「変わりうるもの（変動性、volatility）」ごとに構成要素へ分け、変化をその構成要素の中に閉じ込める方法である。構成要素は Client・Manager・Engine・ResourceAccess・Utility の層に置き、層の間の呼び出し方に規則を設ける。

## 構成

| # | ドキュメント | 内容 | 主な ID |
| --- | --- | --- | --- |
| 0 | [要件定義](00_requirements.md) | ビジネス要件、機能要件、非機能要件、コアユースケース、未決事項 | BR / FR / NFR / UC / OPEN |
| 1 | [概要設計](01_overview.md) | 範囲と既存のクレートとの比較、変わらないもの（ライブラリの核）、変動性の分析、階層構成、リソース、利用規則、クレートの分け方 | VOL / CMP / RES |
| 2b | [基本設計（内部）](02_basic_internal.md) | 共通の概念、構成要素の責務と契約（型の層・値の層）、コールチェーン、変動性への対応の確認、実装のフェーズ | CMP / CC |
| 2a | [基本設計（外部）](02_basic_external.md) | インターフェースの設計。外部に提供するもの（公開する API、利用者が実装する trait、コンパイルエラーの文）と、外部から利用するもの（言語・ツール・ライブラリ）の一覧 | API / EXT / ERR / USE |
| 3 | 詳細設計（予定） | 型レベルの表現、アルゴリズム、ファイル配置 | DD |
| 4 | テスト仕様（予定） | 単体・結合・コンパイル失敗・アーキテクチャ・非機能・変動性シナリオ | TC |
| T | [トレーサビリティ表](traceability.md) | 上記 ID の上流から下流への対応と、その逆引き | — |

外部設計（2a）は、インターフェースの設計である。次の 2 つを一覧にする。

- **外部に提供するインターフェース**：公開する API、利用者が実装する trait（拡張点）、コンパイルエラーの文
- **外部から利用するもの**：Rust の言語と標準ライブラリ（`core`）、コンパイラの診断機能（`#[diagnostic::on_unimplemented]`）、開発だけで使うクレート（コンパイル失敗のテストなど）、CI（GitHub Actions）

内部（2b）で構成要素の契約を決めてから、それを外部にどう見せるか（2a）を決める。

## 開発の進め方

| フェーズ | 内容 | 完了条件 |
| --- | --- | --- |
| 0 | 設計ドキュメント（00 → 01 → 2b → 2a → 03 → 04、トレーサビリティ） | 一式がレビュー済みで `main` にある |
| 1〜9 | 実装（[2b §2b.6](02_basic_internal.md#2b6-実装のフェーズ) のフェーズに従う） | 各フェーズで動くようになるユースケースのテストが通る |

- 設計ドキュメントは 1 文書につき 1 つの PR にする。前の PR がマージされるまで、次の PR は作らない。
- 各フェーズの完了時に振り返りを行い、`docs/retrospectives/` に記録する。
- 開発の決まりは、ホームページの [開発の決まり](https://github.com/fukugyononuko/fukugyononuko.github.io/blob/main/docs/README.md#開発の決まり) に従う。

## ID の規則

| 接頭辞 | 意味 | 定義場所 |
| --- | --- | --- |
| `BR-nn` | ビジネス要件 | 00 |
| `FR-nn` | 機能要件 | 00 |
| `NFR-nn` | 非機能要件 | 00 |
| `UC-nn` | コアユースケース | 00 |
| `OPEN-nn` | 未決事項 | 00 |
| `VOL-nn` | 変動性 | 01 |
| `RES-nn` | リソース | 01 |
| `CMP-Xnn` | 構成要素（X = C: Client、M: Manager、E: Engine、A: ResourceAccess、U: Utility） | 01 / 2b |
| `CC-nn` | コールチェーン | 2b |
| `API-nn` | 公開する API | 2a |
| `EXT-nn` | 利用者が実装する trait（拡張点） | 2a |
| `ERR-nn` | コンパイルエラーの文 | 2a |
| `USE-nn` | 外部から利用するもの | 2a |
| `DD-nn` | 詳細設計の項目 | 03 |
| `TC-Xnn` | テストケース（X = U: 単体、I: 結合、F: コンパイル失敗、A: アーキテクチャ、N: 非機能、R: 変動性シナリオ） | 04 |

- ID は一度振ったら番号を変えない。項目を廃止するときは削除せず「廃止」と書く。
- 設計を変える PR では、関係する ID の記述と [traceability.md](traceability.md) を同じ PR で更新する。
- 状態は「初期」（初期版で実装）と「将来」（設計上の置き場所だけ用意し、実装はしない）の 2 種類。

## 表記

- 数式は TeX で書く。文中の数式は $`…`$ の形で書く（`$…$` の形は、隣に全角の記号があると GitHub で数式として表示されないため）。独立した行の数式は ```` ```math ```` のコードブロックで書く。
- 人名は英語で書く（Einstein、Jacobi など）。
