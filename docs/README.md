# 設計ドキュメント

tensorcheck の設計ドキュメント一式。
アーキテクチャは Juval Löwy『Righting Software』の **The Method**（変動性に基づく分解）に従う。

## 構成

| # | ドキュメント | 内容 | 主な ID |
| --- | --- | --- | --- |
| 0 | [要件定義](00_requirements.md) | ビジネス要件、機能要件、非機能要件、コアユースケース、未決事項 | BR / FR / NFR / UC / OPEN |
| 1 | 概要設計（予定） | 範囲、変わらないもの（ライブラリの核）、変動性の分析、階層構成、利用規則 | VOL / CMP |
| 2b | 基本設計（内部）（予定） | 構成要素の責務と契約、コールチェーン | CMP / CC |
| 2a | 基本設計（外部）（予定） | 公開する API、利用者が実装する trait、エラー文 | API / EXT / ERR |
| 3 | 詳細設計（予定） | 型レベルの表現、アルゴリズム、ファイル配置 | DD |
| 4 | テスト仕様（予定） | 単体・結合・コンパイル失敗・アーキテクチャ・非機能・変動性シナリオ | TC |
| T | [トレーサビリティ表](traceability.md) | 上記 ID の上流から下流への対応と、その逆引き | — |

ライブラリには画面がないので、「外部」は利用者から見える部分（公開する API、利用者が実装する trait、コンパイルエラーの文）を指す。
内部（2b）で構成要素の契約を決めてから、それを利用者にどう見せるか（2a）を決める。

## 開発の進め方

| フェーズ | 内容 | 完了条件 |
| --- | --- | --- |
| 0 | 設計ドキュメント（00 → 01 → 2b → 2a → 03 → 04、トレーサビリティ） | 一式がレビュー済みで `main` にある |
| 1 以降 | 実装（フェーズの分け方は 01 と 2b で決める） | — |

- 設計ドキュメントは 1 文書につき 1 つの PR にする。前の PR がマージされるまで、次の PR は作らない。
- 各フェーズの完了時に振り返りを行い、`docs/retrospectives/` に記録する。
- 開発の決まりは、ホームページの [開発の決まり](https://github.com/fukugyononuko/fukugyononuko.github.io/blob/main/docs/README.md#開発の決まり) に従う。

## ID の規則

| 接頭辞 | 意味 | 定義場所 |
| --- | --- | --- |
| `BR-nn` | ビジネス要件 | 00 |
| `FR-nn` | 機能要件 | 00 |
| `NFR-nn` | 非機能要件 | 00 |
| `UC-nn` | コアユースケース | 00 |
| `OPEN-nn` | 未決事項 | 00 |
| `VOL-nn` | 変動性 | 01 |
| `CMP-Xnn` | 構成要素（X = C: Client、M: Manager、E: Engine、A: ResourceAccess、U: Utility） | 01 / 2b |
| `CC-nn` | コールチェーン | 2b |
| `API-nn` | 公開する API | 2a |
| `EXT-nn` | 利用者が実装する trait（拡張点） | 2a |
| `ERR-nn` | コンパイルエラーの文 | 2a |
| `DD-nn` | 詳細設計の項目 | 03 |
| `TC-Xnn` | テストケース（X = U: 単体、I: 結合、F: コンパイル失敗、A: アーキテクチャ、N: 非機能、R: 変動性シナリオ） | 04 |

- ID は一度振ったら番号を変えない。項目を廃止するときは削除せず「廃止」と書く。
- 設計を変える PR では、関係する ID の記述と [traceability.md](traceability.md) を同じ PR で更新する。
- 状態は「初期」（初期版で実装）と「将来」（設計上の置き場所だけ用意し、実装はしない）の 2 種類。
